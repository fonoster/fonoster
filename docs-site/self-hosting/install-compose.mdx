In this tutorial you install Fonoster on one machine. At the end, every service is running and you
are signed in to the dashboard as the owner, ready to make your first call.

## Before you begin

You need:

- [Docker](https://docs.docker.com/get-docker/) with Compose v2 (`docker compose version` prints
  `v2` or later).
- `curl` and `openssl`.
- About 6 GB of free disk for the images.

<Note>
  Fonoster uses ports `443` and `80` (dashboard and API over HTTPS, and its redirect), `5060` UDP
  and TCP (SIP), the UDP ranges
  `10000-10999` and `11000-11999` (call media), and, on localhost only, `4222` (NATS) and `9000-9001`
  (MinIO). Stop anything else that uses them, such as another Fonoster install, or change the ports
  in step 2.
</Note>

<Warning>
  On Linux, turn off Docker's userland proxy before you start. Otherwise Docker starts one
  `docker-proxy` process per published media port, about 4,000 of them, and the machine runs out of
  memory: containers are killed one by one until none is left. Add this to
  `/etc/docker/daemon.json` (merge it if the file already has settings) and restart Docker:

  ```bash
  echo '{ "userland-proxy": false }' | sudo tee /etc/docker/daemon.json
  sudo systemctl restart docker
  ```

  Docker then forwards the ports with iptables rules instead. Docker Desktop on macOS and Windows
  doesn't need this.
</Warning>

<Note>
  If this machine ran Fonoster 0.27 or older with Docker Compose, stop it first: run
  `docker compose down` in its folder. Don't remove its volumes. The new install doesn't use them.
</Note>

## Install Fonoster

<Steps>
  <Step title="Download the release">
    Download the release and unpack it into a new `fonoster` folder:

    ```bash
    curl -fsSL https://github.com/fonoster/fonoster/releases/download/v0.42.0/fonoster-0.42.0.tar.gz | tar xz
    cd fonoster
    ```

    The folder holds `init.sh`, `compose.yaml`, `compose.http.yaml` (plain HTTP behind your own TLS
    proxy), `compose.tls.yaml` (SIP over TLS), `compose.external-db.yaml` (your own Postgres),
    `compose.region.yaml` (a private region), a `config` folder with one file per service, an
    `ansible` folder (the playbook that installs private regions) and a `README.md`.
  </Step>

  <Step title="Generate the configuration">
    Run `init.sh` to generate the secrets and keys, find this machine's address, and set the SIP
    port. It needs only a shell and `openssl`:

    ```bash
    ./init.sh
    ```

    It prints what it wrote and how to reach the install:

    ```text
    .env written (12 secrets generated)
    keys: 3 files created in config/keys
    tls: local CA and server certificate created in config/tls for localhost, 127.0.0.1, 203.0.113.10 (for getting started)
    config: config/routr-edgeport.yaml SIP port 5060
    host address: 203.0.113.10

    Dashboard   https://203.0.113.10
    API         203.0.113.10:443 (gRPC and gRPC-Web, TLS)
    SIP         203.0.113.10:5060 (UDP and TCP)

    Files       /opt/fonoster/.env            Compose settings and the generated secrets (back it up)
                /opt/fonoster/config/         one file per service, yours to edit
                /opt/fonoster/config/keys/    signing keys
                /opt/fonoster/config/tls/     certificate generated for getting started

    Certificate /opt/fonoster/config/tls/ca.pem
                SHA-256 3F:9A:...
                Generated for getting started: browsers show a warning once, and API clients
                trust this CA file (--ca-file, or FONOSTER_CA_FILE). Use a real certificate
                (TLS_CERT and TLS_KEY) before going live: https://docs.fonoster.com/self-hosting/https

    Next: docker compose up -d
    Run ./init.sh again any time to print this. It keeps every secret.
    ```

    The host address is the one softphones, carriers and browsers use to reach this machine. To use a
    different one, run `./init.sh --host-ip <address>`.

    `init.sh` also generates a certificate in `config/tls/`, so Fonoster serves HTTPS from its first
    start. It's for getting started: use a real certificate before you go live
    ([Serve over HTTPS](/self-hosting/https)).

    <Tip>
      To change a port, edit it in `.env` (for example `HTTPS_PORT=8443` or `SIP_PORT=5060`), run
      `./init.sh` again, then `docker compose up -d`. `init.sh` keeps every secret. To run a second
      install on the same machine, also give it its own `COMPOSE_PROJECT_NAME` and `SUBNET_PREFIX`,
      and move every port in the note above.
    </Tip>
  </Step>

  <Step title="Start Fonoster">
    Start every service in the background:

    ```bash
    docker compose up -d
    ```

    The first start downloads the images, which can take 10 minutes or more. Then list the services to see
    them running:

    ```bash
    docker compose ps
    ```

    You see `apiserver`, `autopilot`, `dashboard`, `envoy`, `appbridge`, `roomr`, `minio`, `nats`,
    `postgres`, `routr` and `rtpengine`, each `Up`.
  </Step>

  <Step title="Create your login">
    Create the first user once. Put a password in a file only you can read, then pass it on stdin, so
    it never shows on screen or in your shell history:

    ```bash
    (umask 077; openssl rand -hex 16 > owner.pw)
    docker compose exec -T apiserver fonoster-owner create you@example.com < owner.pw
    ```

    It prints `created you@example.com and its workspace`. Keep the password in your password
    manager, then delete `owner.pw`. Running the command again changes nothing.
  </Step>

  <Step title="Sign in to the dashboard">
    Open the dashboard address in your browser. It warns that the connection isn't private, because
    the certificate is the one `init.sh` generated: open the details and continue to the site. Your
    browser remembers the choice. Then sign in with the owner's email and password, and on **Choose
    a workspace**, select your workspace.
  </Step>
</Steps>

<Check>
  Fonoster is running and you are signed in as the owner.
</Check>

## Where your files are

Everything lives in the `fonoster` folder:

| Path           | What it holds                                                    |
| -------------- | ---------------------------------------------------------------- |
| `.env`         | Ports, the host address, the owner's login and every generated secret |
| `config/`      | Each service's settings, one file per service, yours to edit. They name secrets as `${NAME}`; Compose passes each container only the values its own file names (its `environment:` list in `compose.yaml`) |
| `config/keys/` | The signing keys. Only the API server mounts Identity's private key; AppBridge gets the public key and its call-record key |
| `config/tls/`  | The certificate `init.sh` generated for getting started: `ca.pem` (give it to API clients), the server certificate Envoy serves, and their private keys. Not used once you set `TLS_CERT` and `TLS_KEY` |

<Warning>
  Back up `.env`, `config/keys/` and the `config/` files you edited. The encryption key in `.env` protects the vendor keys you store, and they can't be recovered
  without it.
</Warning>

To change a setting, edit `config/<service>.yaml`, then recreate that service. For example, after you
edit `config/appbridge.yaml`:

```bash
docker compose up -d --force-recreate appbridge
```

A bad file stops the service at start, and `docker compose logs <service>` names the key. When you
upgrade, apply your edits to the new release's files, see [Upgrade](/self-hosting/upgrade).

## Add platform keys

Calls need at least a text-to-speech vendor. Fonoster offers every vendor in its catalog to every
workspace, and calls use your platform key for that vendor unless the workspace added its own in the
dashboard under **Vendor keys**.

The release's config files hold a placeholder platform key for each vendor, such as
`YOUR_DEEPGRAM_API_KEY`. Replace the placeholder with your key:

| Vendor            | File                     | Setting                                    |
| ----------------- | ------------------------ | ------------------------------------------ |
| Deepgram          | `config/appbridge.yaml`  | `providers.deepgram.credential.value`      |
| ElevenLabs        | `config/appbridge.yaml`  | `providers.elevenlabs.credential.value`    |
| OpenAI            | `config/autopilot.yaml`  | `credentials.openai.value`                 |
| Groq              | `config/autopilot.yaml`  | `credentials.groq.value`                   |

For example, this line in `config/appbridge.yaml` sets the Deepgram key:

```yaml config/appbridge.yaml
  deepgram: { adapter: deepgram, capabilities: [tts, stt], credential: { value: "4f1c9a27d0b8e6a3c5f2d7b9e1a4c8f0d3b6e9a2" } }
```

Then recreate the two services that read them:

```bash
docker compose up -d --force-recreate appbridge autopilot
```

<Note>
  A vendor whose placeholder you leave in place is still offered, and its calls fail until a key is
  set. If the dashboard's **Vendor keys** page says no vendors are configured, the catalog has no
  vendor left that takes a key.
</Note>

## Serve over HTTPS

Fonoster serves the dashboard and API over HTTPS from its first start, with the certificate `init.sh`
generated in `config/tls/`. It gets you started: browsers warn once, and the CLI and SDK trust it
through `config/tls/ca.pem` (`--ca-file`, or `FONOSTER_CA_FILE`). Before you go live, replace it with
a real certificate for your domain, see [Serve over HTTPS](/self-hosting/https).

If you already run a TLS proxy (Caddy, nginx, Traefik, a load balancer), serve plain HTTP behind it
instead: set `COMPOSE_FILE=compose.yaml:compose.http.yaml` and `HTTP_BIND=127.0.0.1` in `.env`.

## Use your own Postgres

The install runs its own Postgres. To use one you manage instead, point every service at it before
the first start, see [Use an external Postgres](/self-hosting/external-database).

## Let carriers and phones reach you

A new install names trunks and domains under `fonoster.local`, which works only on your own
network. To give them a domain you own, point DNS at this machine and open the SIP and audio ports,
see [Connect carriers and phones](/self-hosting/carriers-and-phones).
