In this tutorial you install Fonoster on one machine. At the end, every service is running and you
are signed in to the dashboard as the owner, ready to make your first call.

## Before you begin

You need:

- [Docker](https://docs.docker.com/get-docker/) with Compose v2 (`docker compose version` prints
  `v2` or later).
- [Node.js 22](https://nodejs.org/en/download/) or later. You use it to run the setup tool with `npx`.
- `curl`.
- About 6 GB of free disk for the images.

<Note>
  Fonoster uses ports `443` and `80` (dashboard and API over HTTPS, and its redirect), `5060` UDP
  and TCP (SIP), the UDP ranges
  `10000-10999` and `11000-11999` (call media), and, on localhost only, `4222` (NATS) and `9000-9001`
  (MinIO). Stop anything else that uses them, such as another Fonoster install, or change the ports
  in step 2.
</Note>

<Warning>
  On Linux, turn off Docker's userland proxy before you start. Otherwise Docker starts one
  `docker-proxy` process per published media port, about 4,000 of them, and the machine runs out of
  memory: containers are killed one by one until none is left. Add this to
  `/etc/docker/daemon.json` (merge it if the file already has settings) and restart Docker:

  ```bash
  echo '{ "userland-proxy": false }' | sudo tee /etc/docker/daemon.json
  sudo systemctl restart docker
  ```

  Docker then forwards the ports with iptables rules instead. Docker Desktop on macOS and Windows
  doesn't need this.
</Warning>

<Note>
  If this machine ran Fonoster 0.27 or older with Docker Compose, stop it first: run
  `docker compose down` in its folder. Don't remove its volumes. The new install doesn't use them.
</Note>

## Install Fonoster

<Steps>
  <Step title="Download the release">
    Download the release and unpack it into a new `fonoster` folder:

    ```bash
    curl -fsSL https://github.com/fonoster/fonoster/releases/download/v0.31.0/fonoster-0.31.0.tar.gz | tar xz
    cd fonoster
    ```

    The folder holds `compose.yaml`, `compose.http.yaml` (plain HTTP behind your own TLS proxy),
    `compose.tls.yaml` (SIP over TLS), `.env.example`, a `config` folder with one example per service
    and their schemas, and a `README.md`.
  </Step>

  <Step title="Generate the configuration">
    Run `init` to generate the secrets and keys, find this machine's address, and write the
    configuration:

    ```bash
    npx -p @fonoster/common fonoster-config init
    ```

    It prints what it wrote:

    ```text
    .env written (10 secrets generated)
    keys: 3 files created in config/keys
    config: config/appbridge.yaml, config/autopilot.yaml, config/fonoster.yaml, config/roomr.yaml, config/routr-edgeport.yaml, config/routr-one.yaml
    tls: local CA and server certificate created in config/tls for localhost, 127.0.0.1, 192.0.2.10 (for getting started)
    host address: 192.0.2.10

    Next: docker compose up -d
    Then: npx -p @fonoster/common fonoster-config info (dashboard URL and owner login)
    ```

    The host address is the one softphones, carriers and browsers use to reach this machine. To use a
    different one, run `init` again with `--host-ip <address>`.

    `init` also generates a certificate in `config/tls/`, so Fonoster serves HTTPS from its first
    start. It's for getting started: use a real certificate before you go live
    ([Serve over HTTPS](/self-hosting/https)).

    <Tip>
      To change a port, edit it in `.env` (for example `HTTPS_PORT=8443` or `SIP_PORT=5060`) and run
      `init` again, then `docker compose up -d`. `init` keeps every secret and only updates the
      configuration. To run a second install on the same machine, also give it its own
      `COMPOSE_PROJECT_NAME` and `SUBNET_PREFIX`, and move every port in the note above.
    </Tip>
  </Step>

  <Step title="Check the configuration">
    Validate the configuration before you start:

    ```bash
    npx -p @fonoster/common fonoster-config check
    ```

    Each service reports `valid`:

    ```text
    config/appbridge.yaml: valid
    config/autopilot.yaml: valid
    config/fonoster.yaml: valid
    config/roomr.yaml: valid (no schema; values only)
    config/routr-edgeport.yaml: valid (no schema; values only)
    config/routr-one.yaml: valid (no schema; values only)
    ```
  </Step>

  <Step title="Start Fonoster">
    Start every service in the background:

    ```bash
    docker compose up -d
    ```

    The first start downloads the images, which can take 10 minutes or more. Then list the services to see
    them running:

    ```bash
    docker compose ps
    ```

    You see `apiserver`, `autopilot`, `dashboard`, `envoy`, `appbridge`, `roomr`, `minio`, `nats`,
    `postgres`, `routr` and `rtpengine`, each `Up`.
  </Step>

  <Step title="Get your login">
    Print the dashboard address and the owner's login:

    ```bash
    npx -p @fonoster/common fonoster-config info
    ```

    ```text
    Dashboard   https://192.0.2.10
    Owner       admin@fonoster.local / <generated password>
    API         192.0.2.10:443 (gRPC and gRPC-Web, TLS)
    SIP         192.0.2.10:5060 (UDP and TCP)

    Files       /home/you/fonoster/.env   Compose settings and the generated secrets (back it up)
                /home/you/fonoster/config/   service settings (from config/*.example.*)
                /home/you/fonoster/config/keys/   signing keys
                /home/you/fonoster/config/tls/   certificate generated for getting started

    Certificate /home/you/fonoster/config/tls/ca.pem
                SHA-256 3F:9A:…
                Generated for getting started: browsers show a warning once, and API clients
                trust this CA file (--ca-file, or FONOSTER_CA_FILE). Use a real certificate
                (TLS_CERT and TLS_KEY) before going live: https://docs.fonoster.com/self-hosting/https
    ```
  </Step>

  <Step title="Sign in to the dashboard">
    Open the dashboard address in your browser. It warns that the connection isn't private, because
    the certificate is the one `init` generated: open the details and continue to the site. Your
    browser remembers the choice. Then sign in with the owner's email and password, and on **Choose
    a workspace**, select your workspace.
  </Step>
</Steps>

<Check>
  Fonoster is running and you are signed in as the owner.
</Check>

## Where your files are

Everything lives in the `fonoster` folder:

| Path           | What it holds                                                    |
| -------------- | ---------------------------------------------------------------- |
| `.env`         | Ports, the host address, the owner's login and every generated secret |
| `config/`      | Each service's settings, written by `init` from the examples. They name secrets as `${NAME}`; Compose passes each container only the values its own file names (its `environment:` list in `compose.yaml`) |
| `config/overrides/` | Your own settings, such as platform keys. `init` merges each file over the one it writes with the same name and never changes them |
| `config/keys/` | The signing keys. Only the API server mounts Identity's private key; AppBridge gets the public key and its call-record key |
| `config/tls/`  | The certificate `init` generated for getting started: `ca.pem` (give it to API clients), the server certificate Envoy serves, and their private keys. Not used once you set `TLS_CERT` and `TLS_KEY` |

<Warning>
  Back up `.env` and `config/overrides/`. The encryption key in `.env` protects the vendor keys you store, and they can't be recovered
  without it.
</Warning>

## Add platform keys

Calls need at least a text-to-speech vendor. Fonoster offers every vendor in its catalog to every
workspace, and calls use your platform key for that vendor unless the workspace added its own in the
dashboard under **Vendor keys**.

`init` writes a placeholder platform key for each vendor. Put your keys in `config/overrides/`, not
in the files `init` writes: `init` rebuilds `config/*.yaml` every time it runs (when you turn on
HTTPS, or upgrade) and merges each file in `config/overrides/` over the one with the same name, so
your keys stay.

| Vendor            | Override file                     | Setting                                    |
| ----------------- | --------------------------------- | ------------------------------------------ |
| Deepgram          | `config/overrides/appbridge.yaml` | `providers.deepgram.credential.value`      |
| ElevenLabs        | `config/overrides/appbridge.yaml` | `providers.elevenlabs.credential.value`    |
| OpenAI            | `config/overrides/autopilot.yaml` | `credentials.openai.value`                 |
| Groq              | `config/overrides/autopilot.yaml` | `credentials.groq.value`                   |

An override holds only the settings you change. This one sets the Deepgram key:

```yaml config/overrides/appbridge.yaml
providers:
  deepgram:
    credential:
      value: "4f1c9a27d0b8e6a3c5f2d7b9e1a4c8f0d3b6e9a2"
```

Write the configuration again so the overrides are merged in:

```bash
npx -p @fonoster/common fonoster-config init
```

Then restart the two services that read them:

```bash
docker compose restart appbridge autopilot
```

<Note>
  A vendor whose placeholder you leave in place is still offered, and its calls fail until a key is
  set. If the dashboard's **Vendor keys** page says no vendors are configured, the catalog has no
  vendor left that takes a key.
</Note>

## Serve over HTTPS

Fonoster serves the dashboard and API over HTTPS from its first start, with the certificate `init`
generated in `config/tls/`. It gets you started: browsers warn once, and the CLI and SDK trust it
through `config/tls/ca.pem` (`--ca-file`, or `FONOSTER_CA_FILE`). Before you go live, replace it with
a real certificate for your domain, see [Serve over HTTPS](/self-hosting/https).

If you already run a TLS proxy (Caddy, nginx, Traefik, a load balancer), serve plain HTTP behind it
instead: set `COMPOSE_FILE=compose.yaml:compose.http.yaml` and `HTTP_BIND=127.0.0.1` in `.env`.

## Let carriers and phones reach you

A new install names trunks and domains under `fonoster.local`, which works only on your own
network. To give them a domain you own, point DNS at this machine and open the SIP and audio ports,
see [Connect carriers and phones](/self-hosting/carriers-and-phones).
