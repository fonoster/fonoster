Fonoster serves the dashboard and API over HTTPS from its first start, with a certificate `init.sh`
generates in `config/tls/`. That certificate is for getting started: browsers warn about it, and
API clients have to trust its `ca.pem`. Before you go live, use this page to replace it with a real
certificate for every name you serve, renewed without touching the machine again.

Whatever tool you use, it takes three things: one certificate that covers every name, its files in
`.env`, and Envoy recreated after each renewal so it loads the new files. This page does them
with [certbot](https://certbot.eff.org/) and Let's Encrypt. To use other tools, see
[Other ways](#other-ways).

## Before you begin

You need:

- Fonoster installed with Docker Compose. See [Install with Docker Compose](/self-hosting/install-compose).
- Every name you serve pointing at this machine, for example `app.example.com` for the dashboard and
  `api.example.com` for the SDKs. One name for both works too.
- Ports `80` and `443` free on this machine and open in any firewall in front of it.

Run the commands on this page as root.

## Get a certificate

<Steps>
  <Step title="Install certbot">
    Install certbot from your distribution, and stop Envoy so certbot can use port `80` for the
    first certificate. On Ubuntu and Debian:

    ```bash
    apt-get update && apt-get install -y certbot
    cd /opt/fonoster && docker compose stop envoy
    ```

    The package also installs a timer that runs renewals twice a day.

  </Step>

  <Step title="Get one certificate for every name">
    Get a certificate with one `-d` per name. The first name also names the folder the files land in:

    ```bash
    certbot certonly --standalone --agree-tos --email you@example.com \
      -d app.example.com -d api.example.com
    ```

    The certificate and key are in `/etc/letsencrypt/live/app.example.com/` as `fullchain.pem` and
    `privkey.pem`.

  </Step>
</Steps>

## Use your certificate

<Steps>
  <Step title="Set the three lines in .env">
    In your `fonoster` folder, set these lines in `.env`. `PUBLIC_URL` is the address people open
    the dashboard at:

    ```bash .env
    PUBLIC_URL=https://app.example.com
    TLS_CERT=/etc/letsencrypt/live/app.example.com/fullchain.pem
    TLS_KEY=/etc/letsencrypt/live/app.example.com/privkey.pem
    ```

  </Step>

  <Step title="Apply it">
    Recreate the services that read these lines:

    ```bash
    docker compose up -d
    ```

    Envoy now serves your certificate on `443` and redirects `80` to it. Browsers no longer warn,
    and API clients don't need `--ca-file`. With your certificate, Envoy also tells browsers to keep
    to HTTPS for this host for a year (HSTS). It never does with the generated certificate, so
    you can always click through its warning. Browser calls use `wss://`. Envoy passes them to
    Routr, which also listens for them on port `5063` inside the stack. You don't publish or open
    that port.

  </Step>

  <Step title="Check it">
    Request the dashboard over HTTPS. It answers `200`:

    ```bash
    curl -sI https://app.example.com | head -1
    ```

  </Step>
</Steps>

## Renew automatically

The timer renews the certificate when it has 30 days left. Envoy holds port `80` and reads the
certificate only when its container is created, so add two hooks: one stops Envoy before a renewal,
the other recreates it after.

<Steps>
  <Step title="Add the hooks">
    Write the two hook scripts. Change `/opt/fonoster` if your `fonoster` folder is elsewhere:

    ```bash
    cat > /etc/letsencrypt/renewal-hooks/pre/stop-envoy.sh <<'EOF'
    #!/bin/sh
    cd /opt/fonoster && docker compose stop envoy
    EOF
    cat > /etc/letsencrypt/renewal-hooks/post/start-envoy.sh <<'EOF'
    #!/bin/sh
    cd /opt/fonoster && docker compose up -d --force-recreate envoy
    EOF
    chmod +x /etc/letsencrypt/renewal-hooks/pre/stop-envoy.sh \
      /etc/letsencrypt/renewal-hooks/post/start-envoy.sh
    ```

  </Step>

  <Step title="Try a renewal">
    Run a renewal against Let's Encrypt's test servers, hooks included:

    ```bash
    certbot renew --dry-run
    ```

    It ends with `Congratulations, all simulated renewals succeeded`. certbot reports the hooks'
    progress lines as "error output". They aren't errors.

  </Step>
</Steps>

<Note>
  Each renewal takes the dashboard and API offline for about ten seconds. Calls
  in progress aren't affected: SIP and call audio don't go through Envoy.
</Note>

## Other ways

<AccordionGroup>
  <Accordion title="DNS challenge (no downtime)">
    certbot can prove you own the names through your DNS provider instead of port `80`, so Envoy
    keeps running during renewals. Install your provider's certbot plugin, issue the certificate
    with it instead of `--standalone`, and keep only the post hook.
  </Accordion>

  <Accordion title="A proxy in front">
    If a proxy already terminates TLS (Caddy, nginx, Traefik, a cloud load balancer), serve plain
    HTTP on this machine only and let the proxy hold the certificate:

    ```bash .env
    COMPOSE_FILE=compose.yaml:compose.http.yaml
    HTTP_BIND=127.0.0.1
    PUBLIC_URL=https://app.example.com
    ```

    Run `docker compose up -d`, then point the proxy at `127.0.0.1:8449`. It must forward
    gRPC (HTTP/2) and WebSocket upgrades on `/sip`.

  </Accordion>

  <Accordion title="A certificate from another CA">
    Point `TLS_CERT` and `TLS_KEY` at your PEM files: the certificate chain and the private key.
    After you replace them, recreate Envoy with `docker compose up -d --force-recreate envoy`.
  </Accordion>
</AccordionGroup>

## SIP over TLS

<Accordion title="Accept SIP over TLS on port 5061">
  SIP stays on UDP and TCP `5060`. To also accept SIP over TLS on `5061`, for carriers that require
  it (WhatsApp does), you need a certificate that covers the names carriers connect to, a keystore
  made from it, and a DNS name in Routr's `externalAddrs`.

  <Steps>
    <Step title="Get a certificate that covers the SIP names">
      Carriers reach your trunks at `<label>.pstn.<domain>` (one name per trunk; a linked WhatsApp
      number gets its own), and they open a second connection to the name Routr writes in
      `Record-Route` for mid-call requests such as the carrier's hangup. The certificate's names
      must cover both: the wildcard `*.pstn.<domain>` and one fixed name under it, such as
      `sip.pstn.<domain>`. Your HTTPS certificate covers only `app.` and `api.`, so request one
      more. Let's Encrypt issues wildcards only through the DNS challenge, so use your DNS
      provider's certbot plugin (see [Other ways](#other-ways)) instead of `--standalone`:

      ```bash
      certbot certonly --dns-<provider> \
        -d '*.pstn.example.com' -d sip.pstn.example.com
      ```

      Point the `*.pstn.<domain>` and `sip.pstn.<domain>` DNS records at this machine.
    </Step>
    <Step title="Build the keystore">
      Routr reads the certificate as a PKCS#12 keystore:

      ```bash
      mkdir -p config/tls
      openssl pkcs12 -export -in fullchain.pem -inkey privkey.pem \
        -out config/tls/signaling.p12 -passout pass:<password>
      ```

      The keystore is a copy of the certificate, so rebuild it after each renewal: add the
      `openssl` line and `docker compose up -d --force-recreate routr` to that certificate's
      post hook.
    </Step>
    <Step title="Name the host carriers call back">
      Routr writes `externalAddrs` in `Record-Route` toward carriers. Over TLS the carrier verifies
      that name against your certificate, so it must be the fixed DNS name from step 1, not the IP
      address the file has by default (`${HOST_IP}`). Set it under `spec.signaling` in
      `config/routr-one.yaml`:

      ```yaml config/routr-one.yaml
          externalAddrs: ["sip.pstn.example.com"]
      ```
    </Step>
    <Step title="Turn the TLS listener on">
      Uncomment the `routr` lines in `compose.tls.yaml`, add it to `COMPOSE_FILE`
      (`COMPOSE_FILE=compose.yaml:compose.tls.yaml`), uncomment the `tls` transport in
      `config/routr-edgeport.yaml`, set its `keyStorePassword` to `<password>`, open
      `5061/tcp` in your firewall, and run `docker compose up -d --force-recreate routr`. Carriers and
      softphones then use `transport=tls` on port `5061`.
    </Step>

  </Steps>

Routr validates the carrier's certificate chain against the public CAs the JVM ships, and
speaks TLS 1.2 and 1.3 only. A carrier with a private CA needs a truststore holding that CA:
set `securityContext.trustStore` and `trustStorePassword` in
`config/routr-edgeport.yaml`, then recreate Routr. Over a TLS trunk, call audio is encrypted with SRTP
(`AES_CM_128_HMAC_SHA1_80`, the one suite Routr offers); over `5060` it isn't.

</Accordion>

## Troubleshooting

<AccordionGroup>
  <Accordion title="The browser warns that the connection isn't private">
    That's the certificate `init.sh` generated for getting started. Open the details and continue to
    the site; the browser remembers it. To make the warning go away, use your own certificate
    (above).
  </Accordion>

<Accordion title="The browser warns and won't let you continue">
  The browser remembers HSTS for this host from a visit with a real certificate,
  so it refuses the generated one. In Chrome, open
  `chrome://net-internals/#hsts`, delete the host's domain security policy, and
  reload. Other browsers clear it with the site's data.
</Accordion>

<Accordion title="An API client fails with a certificate error">
  The client doesn't trust the generated certificate. Copy `config/tls/ca.pem`
  from the server and pass it: `--ca-file ca.pem` for the CLI and the region
  agent, the `caFile` option for the SDK, or `FONOSTER_CA_FILE=ca.pem` for any
  of them.
</Accordion>

<Accordion title="The dashboard links point at http://">
  HTTPS is the default, but `PUBLIC_URL` in `.env` still starts with `http://`.
  Set it to `https://` and the certificate's name, then run `docker compose up -d`.
  To keep plain HTTP behind your own TLS proxy, use `compose.http.yaml` (above).
</Accordion>

<Accordion title="Envoy doesn't start after you set TLS_CERT and TLS_KEY">
  Set both, or neither for the generated certificate. Check that the two paths in
  `.env` exist on this machine, and read `docker compose logs envoy`.
</Accordion>

  <Accordion title="certbot can't bind to port 80">
    Something holds port `80`, usually Envoy. Add the hooks above, or stop Envoy before you issue
    the first certificate.
  </Accordion>
</AccordionGroup>
